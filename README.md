## 玩法说明

- **品质 = 每件物品携带的 inc 点数（0–10）**。喷涂机 Mk.I / Mk.II / Mk.III 分别给 1 / 2 / 4 点。
- **线性表**：1 点品质 = 原版 inc 100 的效果，即 **+10% 产出、+25% 电耗**；2 点 = +20% / +50%，4 点 = +40% / +100%，以此类推到 10 点。
- **产物继承**：制造台/熔炉开新一批时，取**所有输入槽的每件平均点数的最小值**作为本批品质，产物继承该品质（多原料取最低，缺料/不同品质混投都按平均后取 min）。
- **"本批原料点数"现在会随存档保留（v0.19.1）**：每开一批原料，制造台会把"这一批的每件平均点数"记在内存里（`inputLevel`），本批产物按这个点数继承品质。v0.19.0 及更早它**只存在内存**，所以读档后正在生产的那一批会退化成"0 点原料"——首批产物点数偏低。v0.19.1 把它写进存档尾块的行星节点 `"inputs":[{"e":entityId,"l":level}]`，读档时恢复；**旧存档没有这个节点就直接跳过**（存档 schema 版本仍是 1，旧档照常读）。
- **"本批原料点数"改为四舍五入（v0.19.1）**：以前按原版整除截断（`总点数 / 件数` 丢掉小数），现在用 `QualityMath.BatchInputLevel`（`(总点数 + 件数/2) / 件数`，再夹到 0–10）。典型场景：一台 **10 点制造台**吃 **6 点原料**，一批 5 件共 29 点（料带混进少量低点数料）——旧算法 `29/5 = 5` 出 **7 点**产物，新算法 `5.8 → 6` 出 **8 点**，与"6 点原料 × 10 点建筑"的直觉一致。
- **建筑品质**：手持带品质的材料建造时，材料品质写入建筑（每件平均点数，0–10）。建筑品质决定两件事：
  - **升品概率（v0.18.0 起改为曲线）**：每生产一个周期，按本栋建筑点数查**与速度/充电/发电同一张每点曲线表**——1..10 点 = `2.5/5/7.5/10/15/20/30/40/60/100 %`（`QualityMath.UpgradeCurveChance`），掷中即让本批产物品质 +1（上限 10）。点数**高于 6**（即 7/8/9 点）时再多判定一次（两次都成则 +2）；点数**达到 10 点**时必定 +2、不掷骰。分馏塔不享受这两条额外规则（保持单次升品）。旧线性公式（`点数 × 1.5%`、上限 60%）仅保留在 `QualityMath.UpgradeChance` 供离线 A/B，线上不再使用。以上参数均为内置常量（v0.15.0 起不再开放 cfg）。
  - **矿机（v0.18.0 起确定性）**：每件矿的升品判定次数 = `floor(建筑点数 / 2)`（2 点→1 次、4 点→2 次、6 点→3 次、10 点→5 次；0/1 点→0 次），**每次必定成功**（内置常量 `minerChancePerPoint` = 100，走 `chance >= 100f` 必中分支、不掷骰），每次成功 +1 点，**单件点数 = 判定次数**。即 2 点矿机固定给产物 +1、4 点固定 +2、10 点固定 +5。大型采矿机（站点型）沿用同一套规则。
  - **分馏塔**：每成功分馏一件，按输入平均点数（`fluidInputInc / fluidInputCount`，即原版 num3）继承品质，再走一次升品判定；出货时把该点数写在物品上（传送带堵住不消耗，下个周期重试）。切换配方会清空该塔未出货的品质池。
  - **速度（P3 阶段1）**：每点建筑品质给本栋制造台/矿机加成（**内置分段曲线**：按点数查固定表 `0/2.5/5/7.5/10/15/20/30/40/60/100 %`，10 点 = **2.00×**；v0.15.0 起曲线模式为内置常量，线性公式已不对玩家开放）。只作用本栋建筑、**不额外耗电**、不改存档字段；`speedBonus=false` 可一键关闭。并行设施 tick 的星球兜底计数见 DEVLOG §17.5。
  - **物流塔充电上限（P3 阶段2a）**：每点建筑品质把本塔**每 tick 可充入的电量上限**（原版 `energyPerTick`）按同一内置曲线表提高（10 点 = 2.00×），并同步把需求 `requiredEnergy` 抬到同样数值——电网供电充足时真实提速，供电不足时按电网比例分配。**总电量上限 `energyMax` 不变、单位时间取电上升**（不是省电）；值每 tick 由原版重算，不写入存档；`chargeBonus=false` 可一键关闭。
  - **A 类五件套（task-16，v0.12.0）**：建筑品质点数驱动五类设施——① 研究站研究速度；② 防御塔射速（高斯/激光/加农/等离子/导弹/近程等离子）；③ 发电机功率（风/光/地热/火/射线）；④ 弹射器与发射井发射速度；⑤ 喷涂机概率 +1 点。①–④ 共用 v0.11.2 的分段曲线（10 点 = **2.00×**），⑤ 用同一张曲线当概率（0 点 0% … 10 点 100%）。全部只放大每 tick 的瞬时参数（研究/开火/发射的 `power`、`EnergyCap_*` 返回值、写入 `cargoPool.inc` 前的值），**不改存档字段、不额外改电耗**；每个功能独立开关，关闭时补丁根本不注册（原版 IL 逐字节等价）。**v0.18.0 新增第八项加成：电力塔类建筑的供电范围**（`PrefabDesc.isPowerNode` 的感应塔/无线输电塔/配电站，`connectDistance` 与 `coverRadius` 按同一张曲线放大，10 点 = 2.00×；内置常量 `PowerRangeBonus=true` 恒开、无 cfg 键；构建落成与读档后都幂等重算，写在原版持久字段 `PowerSystem.nodePool[]` 里）。

- **增产模式的额外产物带品质（v0.16.0 修复）**：插件在给装配机记品质池时用的是 `produced[]` 净增量，而原版取货（`PickFrom`）会扣减 `produced[]`，导致「刚产出的增产额外产物」被同一窗口的取货正好抵消、点数池长期缺口（表现为普通产物多半正常、增产额外产物常 0 点）。现在把同一窗口内的取货次数加回生产量，增产额外产物与普通产物一样按批次品质取点；总产量、增产概率、耗电全部沿用原版。

- **增产剂可用喷涂次数 = 1（v0.19.0）**：增产剂 Mk.I / Mk.II / Mk.III 每件现在都只能喷 **1 次**（原版 12 / 24 / 60 次），喷涂机 600 容量的「格」语义不变（1 件 = 1 格）。实现是改 `ItemProto.HpMax`——原版所有插入（`incCount += count * HpMax`）、取出（反算件数）、tooltip 文本都**活读**这个字段，所以 UI 与物流自动一致。读旧档时罐内旧「次数」按 `ceil(次数 ÷ 原版次数)` 折成「件数」并清掉余数（日志 `[QSystem][spraycount] legacy coater (entity N, item 1143): 604 vanilla spray times (60/item) -> 11 items`），不会读档后喷出 60 倍的量；存档哈希校验（`ABN_ProtoData.CheckProto`）期间临时还原原版值，避免误报「数据异常」弹窗。
- **增产剂可用喷涂次数按点数分级（v0.19.1）**：`HpMax` 仍是 1（罐内 1 件 = 1 次），"这一件能用几次"改成按**该件增产剂自身的品质点数**查表：

  | 每件点数 | 0–2 | 3–4 | 5–6 | 7–8 | 9 | 10 |
  |---|---|---|---|---|---|---|
  | 可用次数 | 1 | 2 | 4 | 5 | 7 | 10 |

  实现是"插前快照 + 插后补差"——插入时先记下插之前罐里有多少、插之后再按表值补齐差额，手插 / 背包插 / 料带插 / 喷涂机自身循环四条路径都覆盖（`P6_SprayUses`）。**取回**不再由原版反算件数（那会把"次数"按 `HpMax=1` 当"件数"还回去，等于凭空复制增产剂），改由 `CargoTraffic.TakeBackItems_Spraycoater` prefix 接管 + 每台喷涂机账本（存档 `"sprayuses":[{"e","i","u"}]`）：每件按 `ceil(投入次数 / 投入件数)` 扣、且**取回件数永远 ≤ 当初投入件数**，反复插拔不会多出增产剂；旧档没有账本时按 `次数 / 10` 保守回退。**Mk.I / Mk.II / Mk.III 每次喷涂给物品加的点数（1 / 2 / 4 点）不变**——本次只改"一件能用几次"，不改"喷一次加几点"。
- **品质回收机（v0.19.0）**：把带品质点数的物品「回炉」成喷涂次数。摆一台**喷涂机**，把带品质点数的物品送进它的**催化剂（增产剂）进料带**（原版放 1141/1142/1143 的那一侧）：喷涂机通电、单件点数 ≥1 时（即**任意带点数的货物**，含 Mk.I 喷过的 1 点/件），整叠物品被**消耗销毁**，点数记入该机账号，**每累计 4 点 = 1 次喷涂次数**灌进原版喷槽（满喷 10 点 = 2 次 + 余 2 点；未喷涂的 0 点货物整叠原样放行、不消耗）。阈值是内部开关 `Patches\P7_Recycler.cs` 的 `MinPerItemValue`（默认 1、**不是 cfg 键**），改成 3 即回到「只收 Mk.III 喷过的」；默认取 1 是因为兑换本身亏损（4 点只换 1 次喷涂次数，而 1 次喷涂最多值 3 点），不需要用阈值防套利。点数账号写在本 Mod 的存档尾块（行星节点 `"recyclers"`，形如 `{"e":entityId,"p":点数,"c":容量}`），读档继续累计；拆掉回收机后 1200 tick 才清理。回收仍走原版耗电；喷槽满 600 次时暂停回收（probe `mode=tankFull`），消耗腾出空间后自动恢复。物品带那一侧照常喷涂、互不影响。**行为级已实机验证**（2026-10-31 用户确认，随后把默认阈值由 3 调到 1 并重新出包）。

## 已知限制（照实说明，不是 bug）

- **拆除返还有已知边界**：只覆盖 GUI 拆除路径（批量/脚本/其它 mod 触发的拆除维持原版 inc=0）；多栋叠放建筑一次拆除时点数作用于整栈物品，未逐件拆分。
- **矿机点数规则（v0.18.0 改为确定性）**：判定次数 = `floor(点数 / 2)`、每次必定成功（内置常量 `minerChancePerPoint` = 100，v0.15.0 起不开放 cfg），所以 2 点矿机固定 +1、4 点固定 +2、10 点固定 +5（1 点仍为 0）；v0.18.0 之前的「每次成功率 = 点数 × 2%」概率公式作废（旧期望 4 点 0.16、10 点 1.0 点/件不再适用）。
- **隔离只覆盖建筑类物品与特定容器**：非建筑物品仍按原版合并；交付包（DeliveryPackage）、手持物品、`AddItem` 指定格路径仍按原版合并；"整理"按钮已被 v0.11.1 的 `StorageComponent.Sort` 前缀覆盖，但界面手动拖拽/拆分（直接写 GRID）仍绕过本补丁，可能把不同点数合并回一格（已知边界，见 DEVLOG §21.7 / §23）。
- **容器隔离的边界（v0.11.3）**：只覆盖玩家可交互的通用 `Default` 储物容器（储物仓、战场分析基站等）；**物流塔内部**（`StationStore` 一种物品一格、整格总点数）、**机甲燃料/弹药/炸弹/战斗机格**、**过滤容器**、**储液罐（`TankComponent`，每罐段一格）** 均不隔离，保持原版平均语义（结构上无法逐件保留点数）；`isolateStorageContainers=false` 时与 v0.11.2 完全一致。
- **优先消耗与蓝图粘贴的边界（v0.11.5；蓝图标记已于 v0.15.0 删除）**：优先消耗只作用于"手持建造 / 蓝图粘贴"的建筑物品消耗步骤，普通取物、分拣器、物流塔、容器进出仍是原版顺序；换手时原手持整叠会放回背包（可能多占一格）；材料不足产生的未付款预建（半透明）**v0.18.0 起由 `P1_DeferredPay` 按补付时实际被扣材料物品的点数落成**（与材料当场充足时一致）。蓝图复制/粘贴**不再携带任何品质标记**（v0.15.0 删除该功能），粘贴落成完全由"实际消耗物品点数"决定；把蓝图分享给未装本 Mod 的玩家也完全按原版处理。**v0.19.2 边界补充**：这里说的"不携带品质标记"只针对**建筑自身品质点数**；**品质筛选设置**（分流器每口规则、分拣器阈值）自 v0.19.2 起会随 Shift 复制、Ctrl+C / Ctrl+V 与蓝图复制/粘贴**各自保留**（`P6_FilterCopy`，蓝图里存成 `BlueprintBuilding.parameters` 尾部的 `QFPB` 9 int 块）；未装本 MOD 的玩家放该蓝图仍能正常落成，只是筛选设置不生效。**v0.17.0 边界补充**：收据只在「同一帧的消费窗口 → 同帧 `BuildFinally`（或 `AddPrebuildDataWithComponents`）且 `protoId`/`itemRequired` 匹配」内有效，任何一环不匹配就退化为原版 0 点（建造本身与耗材不变）；材料不足产生的半透明预建补付由 v0.18.0 的 `P1_DeferredPay` 单独观察 `ConstructionModuleComponent.PlaceItems` 的全额补付并绑定点数（原版要求一次付清，因此这条路径不做换格/拆点、只继承实际被扣物品点数）。
- **A 类五件套的边界（v0.12.0）**：① 研究站加成只作用于研究吞吐（hash 进度），不改变电网耗电与 `research_speed` 存档字段；② 防御塔射速只影响开火间隔，伤害/射程/每发弹药消耗仍按原版；③ 发电机加成作用在 `EnergyCap_*` 的返回值上，因此火力发电机按比例多烧燃料、射线接收站按比例多产（文档化双收益）；④ 弹射器/发射井只影响发射计时增量，帆/火箭本体速度与轨道不变；⑤ 喷涂机 +1 只增加写入物品的 `inc`（上限 `Cargo.kIncLevelMax`=10），不改变喷涂次数/增产剂消耗；对整叠喷涂按整叠总点数判定，已达上限的叠不再加成。
- **品质回收机与喷涂次数 = 1 的边界（v0.19.0）**：① 喷涂机必须**通电**（`powerRatio > 0.1`），断电不回收；回收占用的是**催化剂进料带**那一侧，物品带侧照常喷涂、互不影响；② 只收单件点数 ≥ 1 的物品，即**任意带点数的货物**（含 Mk.I 喷过的 1 点/件）；未喷涂的 0 点物品**整叠原样放行、不消耗**。该阈值是内部开关 `Patches\P7_Recycler.cs` 的 `MinPerItemValue`（默认 1、**不是 cfg 键**，改成 3 = 只收 Mk.III 喷过的）；默认取 1 是因为兑换本身亏损（4 点换 1 次喷涂次数、1 次最多值 3 点），无需靠阈值防套利；③ 产物是原版喷槽里的**喷涂次数**（4 点/次）、不是产出物品；喷槽满 600 次时暂停回收（probe `mode=tankFull`），超出容量的点数留在账号；④ 每机账号（`0..600×4` 点）存在本 MOD 的存档尾块里（`"recyclers"` 节点形如 `{"e":entityId,"p":点数,"c":容量}`，旧档缺 key 跳过、早期 `"o"` 字段读档忽略），**卸载 MOD 后这部分账号丢失**（`.dsv` 仍可被原版读取）；⑤ 喷涂次数改成 1 之后，原本靠「一瓶喷 60 次」堆喷涂次数的玩法不再成立，旧档读入时按 `ceil(次数 ÷ 原版次数)` 折算成件数——**迁移后罐内件数变少是预期行为**；⑥ 若同时装了其它喷涂机 MOD，两者都会改写 `SpraycoaterComponent.InternalUpdate`，加载顺序不确定时以最后注册的为准（本 MOD 用 postfix，任何异常都回退原版）。
- **喷涂次数分级的边界（v0.19.1）**：① `ItemProto.HpMax` 仍为 **1**（每件算一件），实际可用次数由 `P6_SprayUses` 在插入/取回时补差到分级表值，所以**直接读 `HpMax` 显示"1 次"的第三方 UI/tooltip 会与本 MOD 的实际次数不一致**（以本 MOD 的 `[QSystem][sprayuses]` 日志为准）；② 取回件数**夹到 ≤ 投入件数**，旧档没有 `"sprayuses"` 账本时按 `次数 / 10` 回退——**只会少给、不会多给**；③ 账本写在 `.dsv` 尾块里，卸载本 MOD 后账本丢失（但喷槽里已经存在的次数是原版存档字段，仍然保留）；④ 与其它改写 `SpraycoaterComponent.InternalUpdate`/`HpMax` 的 MOD 共存时，加载顺序决定谁生效（本 MOD 的取回是 prefix 接管、插入补差是 postfix，异常一律退回原版）。
- **汇编器越界防护（v0.12.1）**：组装机/装配机的 `AssemblerComponent` 在预热、拆除或对象池复用的帧里可能带一个哨兵级 `entityId`（如 `int.MaxValue`）。旧版会把该 id 直接写进品质数组，`entityId + 1` 溢出导致 `IndexOutOfRangeException`（被日志吞掉，但该 tick 的品质簿记丢失）。v0.12.1 起所有品质数组 setter 统一拒收 `entityId > MaxEntityId`（1,048,576），热路径 Prefix/Postfix 也提前返回，并打一次 `[QSystem] assembler ignored an out-of-range entityId=…`（每次启动最多一条）。
- **分馏塔品质是"双重收益"（首版保留，非 bug）**：输入品质既按原版 `Cargo.accTableMilli` 提高分馏成功率，又通过本 Mod 继承/升品到产物，等于点数同时作用于成功率与产物品质（详见 DEVLOG §12.3、§16）。
- **建筑自身性能强化做了 P3 阶段1 + 阶段2a**：制造台/矿机按建筑品质加速（**不额外耗电**）、物流塔按建筑品质提高充电速度上限（**总电量不变、单位时间取电上升**，是平衡选择非 bug）；船速/运力、能量枢纽等后续阶段未做；**电力塔范围已于 v0.18.0 实现**（感应塔/无线输电塔/配电站的连接距离与覆盖半径随品质曲线放大，10 点 = 2.00×；写在原版持久字段里，拆除重建按新点数重算）。
- **物流塔充电加成的两条已知边界（v0.11.0）**：①`isCollector`/`isVeinCollector`（轨道采集器/矿脉采集器）不调用 `SetPCState`，因此不受充电加成；②`energyPerTick` 虽是存档字段但每 tick 由原版重算，若恰好在加成的同一帧存档，读档后首 tick 最多多充一 tick 的电量（自我修正，无 schema 变化，详见 DEVLOG §22.8）。
- **并行设施 tick 的 planetId 兜底**：后台/并行线程上的建筑用"最近一次串行 tick 的星球"兜底，单机单星球无差异；日志 `[QSystem][speed] … fallback=` 可观测（详见 DEVLOG §17.5）。物流塔充能只用实例字段，不依赖该兜底。
- **存档迁移（v0.11.11）**：旧版本把品质数据写在 `BepInEx\config\DSPQualitySystem\saves\<槽名>.json`。升级后**第一次读旧档**时会把这份 JSON 读进内存（日志 `[QSystem][save] legacy sidecar used for '<槽名>'`），此时**不写回也不删除**——该 `.dsv` 还没有尾块，JSON 仍是唯一副本；等这个存档下一次保存（手动或自动），品质数据写进 `.dsv` 尾部，旧 JSON 随即被删除（`[QSystem][save] removed legacy sidecar …`）。所以想立刻完成迁移：读档后手动保存一次。跨机器拷贝存档只需带 `.dsv` 一个文件。
- 品质数值只用于本 Mod 的产物/建筑逻辑，**不改变物品堆叠上限与传送带规则**。
- **储物仓品质格数的边界（v0.13.0，task-17；v0.19.2 起已停用）**：① 只作用于通用 `EStorageType.Default` 储物容器（储物仓/战场分析基站等）；**物流塔内部**（`StationStore`）、**机甲燃料/弹药/炸弹/战斗机格**、**过滤容器**、**储液罐（`TankComponent`）** 不扩容（与 v0.11.3 容器隔离同口径）；② 存档里的仓库 `size`/`grids` 结构永远是原版值，但**只存在于"额外格"的物品写在本 Mod 的尾块里**——卸载 MOD 后存档仍可读，这些物品会丢失；③ 品质下降/功能关闭时，容器要等"额外格"搬空才会缩回原版格数（期间可能保留几格空位，最长 30 帧重试一次），**不会丢物品**；④ 战场分析基站等自带"禁用格数"（`bans`）的容器，额外格数按"原版可用格数"夹、不会占用禁用格。**v0.19.2 起整条功能停用**（`StorageQualityGridsValue=false`）：储物仓一律用原版格数，不再随点数加格；旧存档尾部残留的溢出格数据读档时静默忽略（只 WarnOnce），上述①–④ 仅作为历史行为参考。
- **分流器/分拣器品质过滤的边界（v0.16.1；UI 入口 v0.17.0 改到原版物品选取器）**：① 分流器只重写「本 tick 每件货往哪个输出口送」这一步，指针轮转（`OutputAlternate`）、过滤器、储物仓回灌（`topId`/`bottomId`）等其余原版逻辑保持；② 规则按**当前这一刻**皮带尾部货物判断，不预读上游；规则口不参与兜底，所以「所有规则口都不匹配」时货只去无规则口；v0.17.1 起命中规则的货在规则口都满时**原地等待**（不溢出到无规则口）——这是与 v0.17.0 的行为差异；③ **v0.17.1 起：有规则就完全接管**——原版输入优先级（`inPriority`）、优先级预设（`prioritySlotPresets`）不再让路，`topId != 0`（上方储物仓）只跳过储物仓回灌、主循环仍接管；未命中规则的货一律只去**没有设规则**的输出口，原版 `outFilter` 完全不参与路由（只作原版面板图标显示）；品质按每件点数判定。已知限制：8 点/0 点这种每件点数由 `货.inc / 货.stack` 取整得出（2 件 1 点 = 0 点），与角标显示一致；④ 分拣器过滤 v0.19.1 起作用于传送带（`CargoPath.TryPickItem` 两个重载）与 `PlanetFactory.PickFrom` 的 `storage`/`assembler`/`ejector`/`silo` 四类来源，`station`/`lab`/`powerGen` 明确跳过（原因见"玩法说明"），发电厂燃料抓取（`CargoPath.TryPickFuel`）仍不受影响；⑤ 分拣器在「抓取窗口（皮带尾部 5 格内）」找第一件合格货，窗口外的货要等它走进窗口；⑥ v0.15 及更早存档里的旧 `splitters:[{"e":…}]` 布尔节点（旧「品质优先」勾选）读档时忽略并打一次性日志 `legacy 'splitters' node ignored`，不做迁移——旧勾选语义与新规则模型不同，强行映射会改变物流行为；⑦ 两个功能都没有玩家 cfg 开关（内置常量默认开启），0 条规则时与不使用本功能的原版完全一致（分流器 Prefix 检测到无规则直接返回原版）；⑧ 编辑器是挂在原版物品选取器底部**一行**（`QSystemFilterPickerRow`），极端窄窗口/极小分辨率下若与该窗口底部元素重叠，属于已知视觉瑕疵、不影响点击（控件都在选取器矩形内、`layer=5`、用真正的 `Button`）。
- **物品品质角标的边界（v0.14.0，P6）**：① 角标显示的是**每件点数** = `inc / 堆叠数` 向下取整——整叠总点数不变但堆叠数增加时每件点数会下降，这是原版 inc 语义（`grid.inc` 是整格总点数）；② 覆盖范围是**玩家背包格**、**打开的储物仓/容器面板格**、**手持物品提示**；机甲燃料/弹药格、物流塔内部等没有独立 `UIStorageGrid` 的界面不显示（它们本来也不隔离品质）；③ **建筑产物悬停预览（装配机/熔炉顶部的大产物图标）刻意不做角标**——那个图标只画配方产物、没有真实 inc 数据；要看产物品质请看同一窗口的产物格/储物仓面板（`servingBox` 网格有角标）；④ 纯视觉、不写存档、不改物品数据，关掉 `itemQualityBadges` 时已有角标立即隐藏、之后不再注册补丁/不再创建对象；⑤ 角标位置锚在图标右上角、字号随格子固定（12px/手持 11px），200% UI 缩放与其它分辨率下若与原版堆叠数字轻微重叠可通过 `itemQualityBadgeStyle=dot` 缓解。

- **视觉标记（P6，v0.11.10；v0.15.0 起只保留金色光环）**：当前星球上点数达到 10 的建筑头顶会显示一圈**金色光环**（256×256 程序生成空心贴图、面向相机、缓慢自转 + 轻微浮动 + 呼吸），浮在建筑最高点上方 1.2m（内置常量）；远处按距离缩小、超过 120m 不画、同屏最多 64 个（按距离取近）。加法混合 + ZTest Always（不被建筑遮挡），纯视觉，不改建筑模型/材质/存档。玩家可用 `tenPointMarkerStyle`（`auto`/`halo`/`none`）、`tenPointHaloSize`、`tenPointHaloPulse`、`tenPointHaloSpin` 调整；**v0.15.0 已彻底删除屏幕描边功能**（原 `tenPointOutline`/`tenPointOutlineWidth`/`tenPointOutlineMax`/`tenPointOutlineOffsetY` 及 `tenPointHaloColor`/`tenPointHaloLift`/`tenPointHaloMax` 均转为内置常量或移除）。

- **v0.16.0 / v0.17.0 建造与采矿修复的边界**：① 大型采矿机（采矿区收集站）的**产物品质**只在「站点把矿从采集器搬进储物格」那一刻结算（原版 `StationComponent.UpdateVeinCollection`），满仓/未发生搬运时不结算、等下一次搬运；整格 `inc` 封顶 `数量 × 10`，站点储物格本身数量上限沿用原版；② 大型采矿机的**放置点数**（建筑自身品质）走与普通建筑相同的「实际消耗物品点数」收据，不再因背包分支丢失；③ Shift+左键立即建造的捕获分两层：优先用同帧「最高品质优先消耗」的收据（`protoId` + `itemRequired` 匹配），收据不可用时才退回「本次 `TakeTailItems` 总点数 ÷ 件数」记录——两层都要求同帧且幽灵建筑 id 有效；若将来官方改动该流程导致条件不匹配，该次会退化为原版 0 点（建造本身与耗材不变）；④ 增产（额外产物）修复只改「记进品质池的数量」，**不改**产物件数、增产概率、耗电、配方与原版 `produced[]`/`productRegister` 语义；⑤ 这几处都沿用 0 点输入 → 0 点输出，不会凭空造品质；⑥ 瞬时消费窗口只在该 tick 内有效（`Time.frameCount` 比较），不会影响普通取物/分拣/物流的消耗顺序。

## R2 / Thunderstore 发布包

`tools\pack-r2modman.py` 生成可直接上传 Thunderstore（或在 r2modman「从文件安装」）的包：

```
python tools\pack-r2modman.py            # 版本号自动取 DSPQualitySystem.csproj 的 <Version>
python tools\pack-r2modman.py --version 0.15.1
```

产物：`dist\DSPQualitySystem-<version>-r2modman.zip`，包内布局：

```
manifest.json                 # Thunderstore manifest v1
icon.png                      # 256x256 PNG
README.md / CHANGELOG.md
BepInEx/plugins/DSPQualitySystem/DSPQualitySystem.dll
```

manifest 硬性约束（脚本会逐项校验，不通过直接失败）：

- `name`：仅字母/数字/下划线，≤ 64 字符；
- `version_number`：`Major.Minor.Patch`，≤ 16 字符；
- `description`：**≤ 250 字符**（Thunderstore 上限），单行；
- `website_url`：空或 http(s) URL，≤ 255 字符；
- `dependencies`：`Namespace-Name-Version` 格式，本包声明 `xiaoye97-BepInEx-5.4.17`、`CommonAPI-CommonAPI-1.6.7`；
- `icon.png`：256x256 PNG、≤ 1 MB。

打包源文件在 `tools\r2\`（`manifest.template.json` / `icon.png` / `README.md` / `CHANGELOG.md`），zip 内文件时间戳固定，重复构建哈希稳定。
